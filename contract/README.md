## Design notes

### Agent protocol: delivery
- **Agent → control plane is reliable and ordered.** Every message carries a per-run `seq`; the runtime keeps it in its on-disk outbox until the control plane acknowledges it, and the control plane acknowledges only after persisting. Duplicates (seq already persisted) are dropped, so delivery is effectively exactly-once. `HelloAck.last_persisted_seq` tells a reconnecting runtime where to resume.
- **Control plane → agent is idempotent, not sequenced.** Commands are keyed (`run_id`, `prompt_id`, `call_id`) and rebuilt from the database after every reconnect. This keeps the control plane stateless per connection, so a reconnect can land on any replica.
- **Request/response pairs** (tool calls): after a reconnect the runtime re-sends pending requests with the same id; the control plane answers from its stored result. Tool calls are persisted anyway for the audit log, so retries never execute twice.
- **No Git credentials over the channel.** The gateway's Git proxy injects the forge credential (iter2-git-proxy). `CredentialRequest`/`CredentialGrant` are removed; `AgentMessage` field 14 and `ControlMessage` field 16 are reserved.
- **Prompt delivery is confirmed by the transcript.** The `UserMessage` event carrying a `prompt_id` marks the queued message as delivered. A prompt that arrives while the runtime is finalizing stays undelivered and triggers the next run.
- **A run waits after a normal turn end.** With no queued prompt the runtime reports `RUN_PHASE_AWAITING_INPUT` and keeps the harness session up. The control plane owns the idle deadline (last `TurnEnded` + `runs.keepAliveSeconds`) and sends `Release`; the run then ends `END_TURN`, or `BLOCKED` if the last turn had a blocking request (`ToolCallResult.await_input_after_turn`). `Prompt` starts the next turn, `Cancel` ends it `CANCELLED`. After `Release` or `Cancel` the control plane sends no more prompts on that run.
- **Queued messages reach the runtime between turns.** The control plane sends a queued prompt when the run starts and after each persisted `TurnEnded`, and marks it as forwarded (`task_messages.forwarded_at`). A prompt queued while a turn is open (a persisted `TurnStarted` without a later `TurnEnded`) stays held back, so a board member can still edit or remove it. A forwarded prompt that is not yet delivered is sent again after a reconnect with the same `prompt_id`.

### Agent protocol: tool calls are typed, not raw MCP frames
Recorded as ADR-0027 (*Accepted*). ADR-0007 mentioned `McpFrame`s. The draft uses typed `ToolCallRequest`/`ToolCallResult` instead:
- The runtime answers `tools/list` locally from `Assign.tools`; only calls cross the stream.
- `call_id` (UUIDv7, generated by the runtime) is the idempotency key and the audit record id.
- The control plane needs no per-run MCP session state, which matters for multi-replica reconnects.
- Scope: this covers the factory tools only. Third-party MCP servers don't use the agent stream; they're reached with native MCP through the gateway (ADR-0032), so they keep features like resources and prompts.
- Factory tools need no MCP features beyond tools; elicitation would map to "ask a human" later anyway.
- `ToolCallResult.end_run_after_turn` lets the control plane end a run (used by `complete_task`) without the runtime special-casing tool names.

### Transcript
- Own schema modelled on ACP `session/update` (ADR-0017). The runtime assigns `turn_id` and `message_id`; `message_id` is the stable DOM id the UI morphs while chunks stream in (ADR-0004).
- Usage is per model per turn (`TurnEnded.usage`), with `usage_source` recording whether the harness reported it or the runtime parsed it from session files. This is the input for "what if" costs (ADR-0021).
- Binary content is inline on the wire; the control plane moves it to the blob store and replaces it with the SHA-256 before storing (ADR-0012).
- In iteration 1 the runtime doesn't advertise ACP's client file-system or terminal capabilities, so Claude Code uses its own tools in the sandbox. That's why there is no terminal content type.

### Integration plugins (WIT)
Recorded as ADR-0028 (*Accepted*). ADR-0018 named the package `darkfactory:forge@0.1.0`. The draft uses **`darkfactory:integrations@0.1.0` with capability interfaces** instead:
- `pull-requests` and `issues` are separate interfaces sharing `types`. Forgejo exports both (world `forge`), an issue-only tracker exports just `issues` (world `issue-provider`). The control plane detects capabilities from the component's exports.
- Commenting on an issue was in the "forge" list for iteration 1, but it's issue-tracker functionality. With separate interfaces, the Forgejo plugin still covers it in one component.
- `find-open` makes PR creation idempotent: if `create` fails with `conflict`, or the control plane crashed between creating the PR and recording it, it looks the PR up instead of opening a second one. It also serves the later "attach to existing PR" mode (ADR-0025).
- `draft` is a forge-neutral flag. Forgejo marks work-in-progress PRs through a title prefix (to verify against its API); the plugin hides that.
- The host links standard WASI with no capabilities granted (no preopens, environment or sockets), so `wasi:http` is the only way out. The host allowlists the configured hosts and injects `Authorization`.
- WASI is pinned to `0.2.12` (what Wasmtime 46 ships). Guests built against older `0.2.x` still link through semver-compatible imports; the host needs a Wasmtime release that provides 0.2.12.

### Factory tools
- `update_pull_request` works before the PR exists: values are stored and applied when the control plane opens the draft PR after the first push.
- `report_progress` sets the task's status line; mirroring it to the issue is project policy, separate from the explicit `comment_on_issue`.
- `set_task_title` sets the task's title with source `agent`; it changes nothing when a person or an earlier call already set a title.
- `complete_task` ends the run after the current turn; the control plane marks the PR ready for review.

### Gateway link
- `GatewayPolicy.PolicyWatch` is served by the control plane and called by every gateway pod; `GatewayLog.Tail` is served by every gateway pod and called by the control plane. Both use the internal port (9444) with mTLS and certificates from the instance CA.
- Every `PolicyUpdate` is a full snapshot (sandbox registry with each run's effective `http-host` allowlist). `version` comes from a database sequence, so it is monotonic across control plane replicas. A gateway enforces its last snapshot while it is disconnected.
- `FlowEvent` is ephemeral: gateway pods keep it in a ring buffer, nothing is persisted. A lagging `Tail` stream receives an event with `gap = true` where events were dropped.
- Git proxy (iter2-git-proxy): `SandboxEntry.git` (`GitRoute`) names the run's upstream repository (`https://` only), its branches as full ref names (`refs/heads/main`, `refs/heads/factory/task/<KEY>`, `refs/heads/factory/wip/<KEY>`) and a `credential_ref` into `Snapshot.forge_credentials`. Route and credential arrive in the same snapshot, so they always match. `ForgeCredential` is secret: never logged, and its Rust `Debug` redacts the password.
- `GatewayGit.RecordPush` is served by the control plane on the internal port (9444) and called by the gateway's Git proxy for every push. `push_id` (UUIDv7) is the idempotency key; the verdict only moves forward (`FORWARDING` → `ACCEPTED` | `UPSTREAM_FAILED`; `REJECTED` is final). The gateway records `FORWARDING` before it sends anything upstream. A `FORWARDING` record without a final call for 10 minutes is marked `unknown` by the control plane; this state exists only in the database, not in the contract enum, and a later `ACCEPTED` or `UPSTREAM_FAILED` replaces it with an audit entry.

## Planned additive changes (no new major version needed)
- `Assign`: skills bundle, project context document (ADR-0026), keep-alive window for `AwaitingInput`, workspace lifecycle hooks (phase, name, command or script, timeout, failure policy — F9).
- `ControlMessage`: `ToolsChanged` for lazy tool loading (`load_server`); `SnapshotWorkspace` for an immediate WIP snapshot (F8).
- WIT: `issues.list`/webhook handling (`handle-webhook`, ADR-0015), PR comments and review data for the review loop, a `repository` capability (compare refs, read a file at a ref, list a tree) for the workspace changes view (F8). Also for ADR-0033: `pull-requests.list-open` with filters (head prefix, author, label) and a `checks` capability (CI status and job logs for a ref or PR). For ADR-0034: `pull-requests.merge` (merge method) and `branches.create` (new branch at a ref).
- Agent protocol: the branch rewrite policy in `Assign.workspace` (ADR-0033). Subtasks based on a parent branch need no change; the parent branch arrives as `Workspace.base_branch` (ADR-0034).
- Factory tools: `ask_question` (text, suggested answers, addressee, blocking) and `request_approval` (type, typed payload, reason, blocking) (ADR-0038). Transcript: request and decision events.
- Factory tools: "create subtask" (assignee, prompt, optional base and settings no looser than the resolved ones) and "merge subtask PR" (ADR-0034).
- Transcript: a hook execution event (phase, name, exit code, duration, output tail) for lifecycle hooks (F9).
- Artifacts, agent-side WASI tools (F2), `Assign.harness` for the built-in loop (inference endpoint URL, model), the gateway MCP endpoint for the harness configuration (ADR-0032).

Not planned: inference messages. Inference goes through the gateway's OpenAI-compatible endpoint, not the agent protocol (ADR-0007, ADR-0029). The gateway's own link to the control plane is a separate contract, `darkfactory.gateway.v1` (see below).

## Open points
1. Transcript ordering across runs: `seq` is per run; the UI's SSE event id would be `(run, seq)` or a global id assigned by the control plane.
2. Correlating harness tool calls (ACP `toolCallId`) with factory calls (`call_id`) is best effort; the MCP request carries no ACP id.
3. Size limits: proposed gRPC max message size 16 MiB; the runtime truncates raw tool input/output above 64 KiB and marks `truncated`.
4. Leftover outbox of a crashed previous run is discarded (with a notice). Git state is recovered by workspace prepare, but the transcript tail of that run is lost.
