# df-web

Rules for the web UI crate, on top of the root `AGENTS.md`.

## Web UI scripts

JavaScript that is code lives in TypeScript files, not in Rust strings.

- Inline `x-data="{ … }"` holds plain data only: flags, strings, numbers, `null`, including values the server fills in. Short expressions in `x-on:*`, `:class` and similar attributes stay inline.
- State with a method, getter or `init()` is an Alpine component in `crates/df-web/scripts/<name>.ts` that calls `Alpine.data('<name>', …)` on `alpine:init`. Add `<name>.js` to `COMPONENT_SCRIPTS` in `crates/df-web/src/layout.rs`, which loads it before Alpine. Server values go in as a JSON argument (`x-data="egressLog({…})"`, escaped by maud).
- Plain scripts are not Alpine components: `sse-cleanup.ts` (an htmx extension, loaded between htmx and `hx-sse` through `SSE_CLEANUP_SCRIPT`), `htmxErrors.ts` (the network error toast) and `focusAfterSwap.ts` (focus after a row was selected) listen on `document` and are listed in `COMPONENT_SCRIPTS`. A script never writes an element ID: the server names it in a `data-*` attribute rendered from `htmx::Region`, or the script navigates relative to its element.
- Files are classic scripts: no `import`/`export`, no bundler. `swc` (pinned, `.swcrc`) compiles each `.ts` to one minified `<name>.js` served under `/assets/`. Responses are compressed and cached by content hash. Bazel builds them in the genrule `:web_scripts`, `build.rs` runs `swc` from `PATH` (or `SWC_BIN`) under plain `cargo`.
- The one exception is the editor bundle: `editor/markdown-editor.ts` is an ES module that imports the CodeMirror packages of `package.json`, and `esbuild` (pinned, `--bundle --minify --format=iife`) turns it into one classic script `/assets/editor.js` that exposes `window.DfMarkdownEditor`. Bazel builds it in the genrule `:editor_bundle` (passed to the build script as `EDITOR_BUNDLE`), `build.rs` runs `esbuild` from `PATH` (or `ESBUILD_BIN`) when the CodeMirror packages are installed, and reports the cfg `df_web_editor` when it embedded the bundle. `markdownField.ts` loads it on demand from `data-editor-src` of `<body>`, which only a build with the bundle has. The bundle must stay below 300 KiB gzip-compressed (a test names the size). Its types are checked by their own project: `npx --yes -p typescript@<version> tsc -p crates/df-web/editor` after `pnpm install --frozen-lockfile` (the `web-typecheck` hook skips it without `node_modules`, CI runs it). A test that reads the bundle gets `#[cfg_attr(not(df_web_editor), ignore = "…")]`.
- Types: `tsconfig.json` is `strict`. The Alpine API and other globals the components use are declared in `scripts/types/*.d.ts`; extend them when a component needs more. Check with `npx --yes -p typescript@<version> tsc -p crates/df-web` (version as in `lefthook.yml`; the `web-typecheck` hook and CI run it).
- Tests read a component's TypeScript source with `crate::assets::script_source("<name>.ts")`; they run in every build. A test that reads compiled output gets `#[cfg_attr(not(df_web_scripts), ignore = "…")]` (compiled scripts), `not(df_web_styles)` (`app_css()`) or `not(all(df_web_scripts, df_web_styles))`, whichever kinds it reads, so that a missing tool never lets it pass silently.
- Stylesheet: `styles/input.css` is compiled by `tailwindcss` (Bazel genrule or `build.rs`). `assets/app.css` is not checked in.
- Third-party scripts: Mermaid, htmx with its SSE extension and Alpine are not checked in. `package.json` pins them, `pnpm-lock.yaml` locks them, and `build.rs` embeds their published dist files under `/assets/vendor/` (table `VENDOR` in `build_assets.rs`). Under plain `cargo`, run `pnpm install --frozen-lockfile` in `crates/df-web` (pnpm as in `packageManager`; `bazel --bazelrc=.bazelrc.agents run //:bazel_env` provides it); without it the build warns and the UI does not work. Bazel (`:vendor_scripts`, `VENDOR_SCRIPTS`) fails without them. A test that reads them gets `#[cfg_attr(not(df_web_vendor), ignore = "…")]`, or `not(all(…))` together with the other kinds it reads. A bump changes only `package.json` and `pnpm-lock.yaml` (Renovate).

## htmx: element IDs, partials, errors and toasts

- Shared element IDs come from `htmx::Region`: an ID that markup sets in one file and a selector (`hx-target`, `hx-select`, a partial of `sse.rs`, a script through a `data-*` attribute) names in another is a `Region`. Use `Region::X.id()` for `id=` and `Region::X.selector()` for the selector. Add the ID to the `regions!` list; a test checks that the IDs are unique and valid.
- Page-local IDs, which only one file sets and selects (`#form` of a single page, `#save-status`), and per-item IDs built with `format!` (`#row-DF-12`), stay literals next to their `id=`.
- Every `<hx-partial>` goes through `htmx::partial(target, swap, inner)`. Do not write the element by hand.
- Error answers go through `auth::error_page` (directly or through `responses::not_found` and `responses::internal_error`). For an htmx request, the `htmx::error_answers` middleware turns that page into a toast in `Region::Toasts` and keeps the status and the headers; a handler that answers an error with another response swaps text or nothing into its target. Invalid forms (422) and conflicts (409) show their message in place and do not use `error_page`.
- Toasts go through `components::toast_answer(status, toast(...))` or `components::error_toast`. The toast region of the layout is the live region, so a toast has no `role` of its own.

## Checking the UI in a browser

With a container socket, `just serve-local` runs the control plane on `http://127.0.0.1:8080` with PostgreSQL and Dex from `compose.yml` (login `admin@example.com` / `password`, `docs/development.md`, section 6). Compare against the PenPot boards as described in `docs/design-workflow.md`. The `obscura` browser has a fixed 1280 px viewport; narrower or wider widths need a browser with viewport control (Playwright MCP).
