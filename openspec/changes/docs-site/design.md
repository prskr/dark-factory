# Design: docs site

## Context

See proposal.md for motivation; requirements are in `specs/`. Prerequisite: change `release-versioning` (version scheme, release workflow, `profile_menu(display_name, version)`, `docs/releasing.md`).

Current state:

- `docs/` holds contributor docs, ADRs and three user guides. `docs/BUILD.bazel` exports `design-system.md` for a df-web test.
- `crates/factory-agent/docs/configuration.md` is read with `include_str!` by `factory-agent` and `df-k8s` tests. The `df-agent-channel` and `df-plugins` references are plain files.
- Pinned tools come from `multitool.lock.json` (generated by `cargo xtask update-tools`) and are put on `PATH` by `build/with_tools.sh` through `//:bazel_env`.
- The web UI ships `crates/df-web/assets/fonts/` (Inter, JetBrains Mono) and `logo.svg`. Tokens are in `crates/df-web/styles/input.css`.
- Hextra requires Hugo extended ≥ 0.146. Hugo modules need Go to download, not to build from `_vendor/`.

## Goals / Non-Goals

**Goals:**

- One `docs/` directory holds everything the site needs. Contributor docs next to it stay plain Markdown readable on GitHub.
- The publish step is a script that can be tested locally against a directory; the workflows only call it.
- The theme override survives Hextra updates: CSS variables and config, no copied theme layouts.

**Non-Goals:**

- Rendering the Markdown identically on GitHub and on the site: rejected; published pages use Hugo front matter and may use Hextra shortcodes.
- Building the site with Bazel: rejected; Hugo is a single binary run through `build/with_tools.sh`, and the site has no Rust inputs.
- Analytics: rejected.

## Decisions

### D1: Two content roots, one Hugo project

```
docs/
  config/
    _default/hugo.yaml     shared config (theme, params, markup)
    _default/module.yaml   docs mounts (content, crate references, fonts)
    landing/module.yaml    landing mounts (landing/ as content, fonts)
  go.mod, go.sum       Hugo module requirement on github.com/imfing/hextra
  _vendor/             output of `hugo mod vendor` (committed)
  content/             docs; the home page of this build is the docs start page
    install.md, operations/{logging,telemetry,keycloak}.md, reference/…
  landing/             landing page content (_index.md)
  assets/css/custom.css, assets/js/versions.js
  layouts/             render hooks and small partials only (no theme copies)
  static/              CNAME, .nojekyll, logo, favicon
  publish.sh           publish script (D4), test in publish_test.sh
  development.md, adr/, …   contributor docs, not under content/, so Hugo ignores them
```

The docs build runs `hugo --baseURL https://www.dark-factory.eu/docs/<slot>/` with the `_default` configuration. The landing build runs `hugo --environment landing --baseURL https://www.dark-factory.eu/`. Its `config/landing/module.yaml` declares its own `module.mounts`, which replaces the docs mount list (Hugo merges maps but replaces lists), so `landing/` is mounted as `content` and the docs tree is not. `--contentDir` is not used: once `module.mounts` declares a `content` mount, the flag no longer selects the content. Each docs version is a self-contained site with its own search index, which gives per-version search without extra work.

- Alternative: one build with `content/_index.md` (landing) and `content/docs/`. Rejected: every versioned build would also contain a frozen landing page, and the docs `baseURL` would have to drop the `/docs` segment that the content path already adds.
- Alternative: the site in a new top-level `website/` directory. Rejected: the user docs already live in `docs/`.

### D2: Hextra as a vendored Hugo module

`docs/go.mod` requires a Hextra release tag; `_vendor/` is committed, so builds need no Go and no network. `just docs-theme-update <tag>` runs `hugo mod get github.com/imfing/hextra@<tag> && hugo mod vendor` and needs Go locally. `_vendor/` is excluded from `typos` and `kingfisher`, and from `cargo xtask check-file-length` (third-party code).

- Alternative: git submodule. Rejected: every checkout needs `submodule update`, and Renovate would track Hextra's `main` instead of its releases.
- Hugo itself is added to the tool list of `cargo xtask update-tools` as the `hugo_extended` asset (Linux amd64 and arm64 archives; macOS universal archive for both CPUs).

### D3: Configuration references through mounts

`config/_default/module.yaml` mounts the three crate `docs/` directories into `content/reference/<name>/`, with `includeFiles: configuration.md`. A mount of `content` replaces the default content mount, so `content` itself is mounted explicitly. This mount list applies to the docs build only (D1). Each `configuration.md` gets YAML front matter (`title`, `weight`); the `include_str!` tests search the text and tolerate it.

- Risk: if Hugo rejects a mount source outside the project directory, the fallback is a copy step in `publish.sh` and in the `just` recipe before the build. Task 1.3 checks this first.

### D4: Publishing with `docs/publish.sh` on the `gh-pages` branch

GitHub Pages serves the `gh-pages` branch, root directory. `publish.sh <site checkout> main` and `publish.sh <site checkout> release <version>` change only what each mode owns:

| Path | Owner |
|---|---|
| `/` (landing output), `/404.html`, `/CNAME`, `/.nojekyll`, `/docs/index.html` | `main` |
| `/docs/dev/` | `main` |
| `/docs/<version>/` | `release` (written once) |
| `/docs/latest/`, `/versions.json` | `release` |

- `release <version>` stops before any write when `<version>` is older than the newest version in `versions.json` (numeric `YYYY.M.N` comparison). The same version is accepted again, so a re-run of a failed docs job replaces its own directory. An old workflow run that is re-run therefore cannot move `latest` back.
- `/docs/index.html` is a meta refresh (plus a link) to `latest/` when `versions.json` lists a release, otherwise to `dev/`. Both modes regenerate it, so the first release switches it.
- `versions.json` is `{"versions": [{"version": "2026.11.1", "latest": true}, {"version": "2026.11.0"}]}`; `dev` is implicit. It is updated with `jq` from multitool.
- The script uses `rsync --delete` per owned directory, never on the site root. `publish_test.sh` runs both modes against a temporary directory and asserts ownership: a `main` run leaves `/docs/2026.11.0/` and `versions.json` untouched, a second release keeps the first, and `release 2026.11.0` after `2026.11.1` fails without changing anything.
- The workflows check out `gh-pages` into a worktree, run the script, and commit and push. Both workflows share `concurrency: gh-pages` without cancellation.
- Alternative: `actions/deploy-pages` with an uploaded artifact. Rejected: each deploy replaces the whole site, so every deploy would have to rebuild or download all versions.

### D5: Switcher and banner in one script

`assets/js/versions.js` is loaded through Hextra's `custom/head-end` partial. Hugo passes it the build's `docsVersion` (`dev` or the release version) and `slot` (`dev`, the version, or `latest`) through `params`, set by `HUGO_PARAMS_DOCSVERSION` and `HUGO_PARAMS_DOCSSLOT`. At page load it fetches `/versions.json`. A failure or a missing file means `dev` only. It then:

- fills a `<select>` placed by a `menu.main` placeholder entry; on change it replaces the `/docs/<slot>/` prefix of the current path;
- inserts the banner above the content. On a release that is not the latest it reads "Docs for 2026.11.0. The latest release is 2026.11.1 →", linking to the same path under `/docs/latest/`. On `dev` it reads "Unreleased: docs for `main`".

The site-root `404.html` comes from the landing build. A script on it reads the slot from the requested path and links to `/docs/<slot>/`.

- Alternative: render the version list at build time. Rejected: frozen builds would never show newer versions.

### D6: Theme through CSS variables

`hugo.yaml` sets `params.theme.default: system` and `displayToggle: true`. `custom.css`:

- `--primary-hue: 135deg; --primary-saturation: 100%;` with `--primary-lightness: 21%` (`accent-text` `#00691a`) in light and `68%` (`#5cff8a`) under `.dark`;
- neutral overrides for page background, text and borders from `app`, `ink`, `muted` and `line` of both themes;
- `@font-face` for Inter and JetBrains Mono. The `woff2` files are mounted from `crates/df-web/assets/fonts/` into `static/fonts/`, so they are not copied.

Values are copied from `input.css`, and a comment names the source. A shared token file is rejected for now, because the site uses about ten values.

### D7: Internal link check in a render hook

`layouts/_markup/render-link.html` checks links to pages: a relative link without a file extension or ending in `.md` (fragment and query removed) is resolved with `.Page.GetPage`, and the build stops with `errorf` naming the page and the link when the target is missing. Relative links with another extension (images, files from `static/`) pass through. Same-site links must be relative: an absolute link to `www.dark-factory.eu` or `dark-factory.eu` stops the build, so no site link escapes the check. Other external links pass through unchecked. Links from published pages to unpublished repository files become absolute `https://github.com/prskr/dark-factory/blob/main/…` URLs in the sources.

### D8: Docs entry in df-web

`profile_menu` gets a Docs link (`target="_blank"`, `rel="noopener"`, Lucide `external-link` icon added to `Icon`, accessible name "Docs (opens in a new tab)"). The URL comes from a constant base `https://www.dark-factory.eu/docs/` plus the version, or `dev`.

## Risks / Trade-offs

- [Hextra updates change the classes or variables that `custom.css` relies on] → the override uses Hextra's documented variables; a visual check is part of `just docs-theme-update`.
- [Hugo mounts outside the project directory are refused] → fallback in D3, checked in the first task.
- [`gh-pages` grows with every release] → about 5 MB per version; pruning is in the backlog.
- [A meta refresh at `/docs/` is slower than a server redirect] → acceptable; it also works offline from a saved copy.
- [The docs link of an air-gapped instance cannot open] → acceptable; out of scope.

## Migration Plan

1. One-time setup from `docs/releasing.md`: DNS records, Pages source `gh-pages` / root, custom domain, Enforce HTTPS.
2. Merge. The first push to `main` creates `gh-pages` with the landing page and `/docs/dev/`; `/docs/` forwards to `dev/`.
3. The next release adds `/docs/<version>/`, `/docs/latest/` and `versions.json`, and `/docs/` switches to `latest/`.

Rollback: disable Pages or revert `gh-pages`. No application data is involved.
