## Context

Today the runtime finalizes `END_TURN` as soon as a turn ends with no queued prompts (`harness::determine_run_outcome`), the control plane deletes the sandbox and maps `end_turn` to `waiting` (`runs::task_status_for`). A follow-up message sets the task `queued` (`df_db::queue_message`) and the scheduler starts a new run: provisioning, clone or fetch, `session/load`. The proto already has `RUN_PHASE_AWAITING_INPUT`, the `runs.state` constraint already allows `awaiting_input`, and the session already forwards messages to a run that is between turns. `iter2-agent-requests` planned the same wait for blocking questions (`Assign.keep_alive`, `run.keepAlive`).

## Goals / Non-Goals

**Goals:** cheap back-and-forth in one run; a status that says "agent is done, review"; a human way to close a task.
**Non-Goals:** closing on PR merge, PR back to draft on reopen, per-project keep-alive, blocking questions (`iter2-agent-requests`).

## Decisions

1. **The control plane owns the idle deadline; the runtime only waits.** The runtime knows nothing about future input (monitors, webhooks, approvals in `iter2-agent-requests`), so it cannot decide how long to stay up. After a normal turn end it reports `AWAITING_INPUT` and `select!`s over the prompt channel, the cancel signal, a new `Release` control message and `sleep(budget_left)`. Only the channel receive has a side effect and an mpsc receive is cancel-safe. The prompt queue gets a `Notify` (create `notified()` and `enable()` before checking the queue). `Release` is a separate message, not `Cancel` with a reason: it finalizes `END_TURN` and nothing is interrupted.
2. **The session computes the deadline from persisted data.** Deadline = timestamp of the run's last persisted `TurnEnded` + `runs.keepAliveSeconds`. The session already has a `cancel_at` timer in its loop; the idle timer sits next to it and is armed while the run is `awaiting_input` and no prompt is in flight. A replica that takes over the stream computes the same deadline, and one that connects after it passed sends `Release` right after the handshake. Before sending `Release` the session moves the run to `finalizing` (decision 5); prompts are never sent to a `finalizing` run, and the existing "undelivered prompts → `queued`" override starts the next run for anything queued later. If no stream is connected at the deadline, the runtime keeps waiting until it reconnects or its budget ends, which bounds the cost.
3. **One setting, `runs.keepAliveSeconds`, default 600.** Matches `runs.cancelGraceSeconds`. `0` releases right after the turn (one extra round trip compared to today, accepted for one code path). 10 minutes of an idle sandbox costs less than a cold start plus a reloaded session and keeps the provider's prompt cache warm. The meaning is "stay up while the next expected input is at most `keepAliveSeconds` away"; for now the only expected input is a human reply right after the turn. Monitors (iteration 3) extend the deadline to a wake-up that is due within `keepAliveSeconds` and otherwise let the run end and queue a prompt when due. The cost trade-off (idle sandbox vs. cold start) does not depend on who sends the input, so no second setting. `iter2-agent-requests` drops `Assign.keep_alive` and its own `run.keepAlive` and sets the deadline for blocking questions in the control plane.
4. **Idle time counts toward the wall-clock budget**, and a budget that ends while idle finalizes `END_TURN`: no work was cut off, so the task should read `waiting`, not `limit_reached`. The control plane's own `Cancel` at budget plus grace is unchanged and stays a backstop.
5. **Task status follows the phase, `finalizing` closes the run for prompts.** `AWAITING_INPUT` sets the run `awaiting_input` and the task `waiting`, unless undelivered messages exist (then the task stays `running`, and the session forwards them at the turn end as today); `RUNNING` sets both back. The phase update and `queue_message` both lock the task row (`SELECT … FOR UPDATE`) in their transaction, so a message queued while the turn ends is never hidden behind `waiting`. `queue_message` decides on "has an active run that is not `finalizing`" instead of on `status = 'running'`: `running` for such a run, otherwise `queued`. `finalizing` is the existing state for "the run is ending"; the control plane now also sets it itself, in the same transaction, before it sends `Release` or the mark-done `Cancel`. The session never forwards prompts to a `finalizing` run, so a message cannot reach a run that is going away and be lost when the turn is interrupted. The unique active-run constraint keeps the next run from starting before the old one ended.
6. **`in_review` instead of a renamed `waiting`.** The runtime cannot tell a question from "finished" at `END_TURN`; only `complete_task` carries that signal. So `completed` outcome → `in_review`, and `completed` becomes human-only. Pre-MVP, so no compatibility shim: one migration extends the check constraint, and existing `completed` rows stay `completed`.
7. **Mark done = status write + cancel.** `POST /tasks/{key}/done` runs one transaction: check the status (not `queued`, `running`, `completed`), set `completed`, move an `awaiting_input` run to `finalizing`, audit, notify. The replica holding the stream sees the `finalizing` run and sends `Cancel` (as for the budget). `end_run` keeps a `completed` task unless undelivered messages exist, so the cancelled run's end cannot flip it back to `waiting`, while a message queued right after "Mark done" still gets a new run (`queued`).
8. **Design first.** The "Status badge" variant set gets "In review"; whether it reuses a tone or gets new `color.status.review.*` tokens is decided in PenPot, and the task header gets a "Mark done" ghost button next to the PR button, both drawn before the markup.

## Risks / Trade-offs

- Idle sandboxes hold cluster resources for up to 10 minutes per task. Mitigation: setting, `0` disables.
- A run whose stream is down at the deadline stays idle until it reconnects or its wall-clock budget ends. Accepted: the runtime reconnects within seconds in practice, and the budget plus the control plane's hard stop bound the worst case.
- `Release` and a new prompt can cross on the wire only if the session sent both; it never sends a prompt to a `finalizing` run, so the race reduces to "message queued after release", which the run-end override handles.
- A run can now span many human turns; the turn budget (`max_turns`) is reached sooner. When it is, the pending prompt makes the task `queued` and a new run continues, which is today's behavior anyway.
- Two in-flight changes (`iter2-agent-requests`, `iter2-cancel`) touch the same requirements; their artifacts are adjusted in this change's first task.
