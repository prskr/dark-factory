# Spec Delta

## Purpose

Defines how Dark Factory signs every commit a run makes with its persona's signing key, without the key ever entering the sandbox: key generation, storage and rotation, the signing service and its guards, and how the sandbox requests signatures.

## ADDED Requirements

### Requirement: One signing key per persona
Every persona SHALL have an Ed25519 SSH signing key, generated by the control plane when the persona is saved, or before its first run if it has none. The private key SHALL be stored only in a Kubernetes Secret in the instance namespace and held only in the control plane's memory. It SHALL never be written to the database, a log or an audit entry, and never sent to a sandbox or a gateway.

#### Scenario: New persona
- **WHEN** a board member creates persona `linus`
- **THEN** a Secret holding an Ed25519 private key for `linus` exists, and the database holds only its public key and fingerprint

#### Scenario: Persona from before the upgrade
- **WHEN** persona `ada` has no key and a run of `ada` is created
- **THEN** a key for `ada` is generated before the run's sandbox is provisioned

#### Scenario: Key not in the sandbox
- **WHEN** the agent searches the sandbox filesystem and environment for the private key
- **THEN** it doesn't find it

### Requirement: Public key on the persona page
The persona form's group "Commits" (approved PenPot board "Personas · edit modal, commits") SHALL show the commit email, the public signing key in OpenSSH format and its SHA-256 fingerprint, each with a copy action, a link to the how-to for registering them on the forge's bot account, and the button "Rotate key". Without a key it SHALL say so instead of showing the key.

#### Scenario: Registering on the forge
- **WHEN** a board member opens persona `linus`
- **THEN** the group "Commits" shows, in this order: the editable "Commit email" `linus@example.org` with its existing hint; "Register the public key and the commit email on the forge's bot account, so that the forge shows this persona's commits as verified."; the link "Verify persona commits on the forge"; the read-only "Public key" `ssh-ed25519 AAAA…`; the read-only "Fingerprint" `SHA256:…`; the button "Rotate key"

#### Scenario: Copy actions
- **WHEN** a board member opens persona `linus` in a secure context
- **THEN** the copy buttons "Copy commit email", "Copy public key" and "Copy fingerprint" copy the full values and show "Copied", like the webhook URL; without a secure clipboard they are hidden

#### Scenario: No key yet
- **WHEN** a board member opens "New persona", or persona `ada` that has no key
- **THEN** the group "Commits" shows the commit email field and "No signing key yet. Save the persona to create it.", and no "Rotate key" button

### Requirement: Key verification on Forgejo
When the instance configuration loads the forge plugin `forgejo`, the group "Commits" of a persona with a signing key SHALL offer "Verify key on Forgejo": the control plane signs the pasted token with the persona's key, with the dialog's "Forgejo domain" as namespace (never `git`), and shows the armored signature. It SHALL audit every signature. Without the `forgejo` plugin the action SHALL not be shown and requests SHALL be refused.

#### Scenario: Forgejo instance
- **WHEN** the instance loads the `forgejo` plugin, a board member registered `linus`'s public key on the bot account, pastes Forgejo's verification token into "Verify key on Forgejo" with the Forgejo domain `forgejo.example.org` and pastes the shown signature back into Forgejo
- **THEN** Forgejo marks the key verified, commits signed by `linus` show as verified on Forgejo, and an audit entry `persona.signing_key.forge_verify` with persona `linus`, the fingerprint, the domain and the board member exists

#### Scenario: Verify dialog
- **WHEN** the instance loads the `forgejo` plugin and a board member chooses "Verify key on Forgejo" (a secondary button left of "Rotate key") on persona `linus`
- **THEN** a dialog titled "Verify the key of Linus on Forgejo" says "In Forgejo, open the bot account's Settings → SSH / GPG keys, choose "Verify" next to this key and copy the token Forgejo shows." and "Paste the token here. Dark Factory signs it with this persona's key; paste the signature back into Forgejo.", with the field "Token" (placeholder "Paste the token from Forgejo"), the field "Forgejo domain" prefilled with the host of the `forgejo` route with the alphabetically first claimed host: its `apiUrl` host, else the claimed host (empty when the plugin claims no host) and the hint "The value after -n in the command Forgejo shows.", and the buttons "Cancel" and "Sign token"

#### Scenario: Token signed
- **WHEN** the board member submits a valid token with "Sign token"
- **THEN** the dialog says "Dark Factory signed the token with the key of Linus. Copy the signature, paste it into Forgejo and choose "Verify"." and shows the read-only "Signature" (the armored block from `-----BEGIN SSH SIGNATURE-----` to `-----END SSH SIGNATURE-----`) with the copy button "Copy signature" and the button "Done"

#### Scenario: Instance without Forgejo
- **WHEN** the instance loads only the `github` plugin and a board member opens persona `linus`
- **THEN** the group "Commits" shows no "Verify key on Forgejo", and a direct request to sign a token is refused

#### Scenario: Invalid token
- **WHEN** a board member submits a token longer than 256 characters or with non-printable characters
- **THEN** the dialog stays open with the token, shows above the buttons "The token could not be signed: <reason>. Copy the token from Forgejo again.", and nothing is signed

#### Scenario: Invalid domain
- **WHEN** a board member submits an empty Forgejo domain, the domain `git`, or a value that is not a hostname (only letters, digits, `.` and `-`, at most 253 characters)
- **THEN** the dialog stays open with its values, shows the reason above the buttons, and nothing is signed

#### Scenario: Not a board member
- **WHEN** a user without the board-member role requests a token signature
- **THEN** the request is refused and nothing is signed

### Requirement: Key rotation
A board member SHALL be able to rotate a persona's signing key. Rotation SHALL replace the key in the Secret and the public key in the database, SHALL write an audit entry `persona.signing_key.rotate` with the old and new fingerprint, and SHALL apply to every later signature and push check. When the persona has active runs, the confirmation SHALL name how many and say that their unpushed commits must be re-signed.

#### Scenario: Rotate
- **WHEN** a board member rotates the key of `linus`
- **THEN** the persona form shows the new public key and fingerprint with the status "Key rotated. Register the new public key on the forge's bot account.", and an audit entry with both fingerprints exists

#### Scenario: Rotate confirmation
- **WHEN** `linus` has no active runs and a board member chooses "Rotate key"
- **THEN** a confirmation titled "Rotate the signing key of Linus?" says "Dark Factory replaces the signing key of this persona. Every commit is signed with the new key from now on." and "Register the new public key on the forge's bot account. Keep the old key there so that earlier commits stay verified.", with the buttons "Cancel" and "Rotate key" (danger style)

#### Scenario: Rotate with active runs
- **WHEN** `linus` has 2 active runs and a board member chooses "Rotate key"
- **THEN** the confirmation's second paragraph says "2 runs of Linus are active. Their commits that are not pushed yet must be re-signed: the next push rejects them, and the agent is told how."

#### Scenario: Rotation fails
- **WHEN** a board member confirms the rotation of `linus` and writing the Secret fails
- **THEN** the confirmation stays open and shows, above the buttons, "The key could not be rotated: <reason>. Reload the page to see the current key, then try again."

#### Scenario: Rotation failed after the Secret was replaced
- **WHEN** a rotation of `linus` replaced the key in the Secret but failed to store the new public key, and a run of `linus` then commits
- **THEN** the database is updated to the Secret's public key with an audit entry `persona.signing_key.reconcile`, and the commit is signed with that key

### Requirement: Commits are signed at commit time
The runtime SHALL configure Git so that every commit made in the workspace is signed with an SSH signature produced by the signing service, by the harness and by the runtime alike, except WIP snapshot commits. If no signature can be obtained, the commit SHALL fail with an error that names the reason.

#### Scenario: Harness commit
- **WHEN** the agent of a run with persona `linus` runs `git commit`
- **THEN** the commit carries an SSH signature that verifies against `linus`'s public key with namespace `git`

#### Scenario: Control plane unreachable
- **WHEN** the agent runs `git commit` while the runtime is disconnected from the control plane for more than 10 seconds
- **THEN** `git commit` fails with a message that signing is unavailable, and no commit is created

#### Scenario: WIP snapshot
- **WHEN** the runtime creates a WIP snapshot commit
- **THEN** the commit has no signature

### Requirement: Signing guards
The signing service SHALL sign only a payload of at most 1 MiB that parses as a Git commit object whose author and committer name and email equal the run's persona identity, for a run that is active. It SHALL refuse any other payload, with a reason, and sign nothing.

#### Scenario: Commit as another identity
- **WHEN** a run of `linus` requests a signature for a commit authored by `ada@example.org`
- **THEN** the request is refused with "author does not match the persona identity" and `git commit` fails

#### Scenario: Not a commit
- **WHEN** a run requests a signature for a tag object or arbitrary bytes
- **THEN** the request is refused and nothing is signed

#### Scenario: Ended run
- **WHEN** a sign request arrives for a run that has ended
- **THEN** it is refused

### Requirement: Signatures are audited
The control plane SHALL write an audit entry `commit.sign` for every signature it produces, with the agent actor (persona, run, task), the key fingerprint and the commit's tree id. It SHALL write an audit entry `commit.sign_refused` for every refusal, with the reason.

#### Scenario: Signed commit
- **WHEN** the agent of `DF-7` (persona `linus`) commits
- **THEN** an audit entry `commit.sign` with persona `linus`, the run and task `DF-7`, `linus`'s fingerprint and the commit's tree id exists

#### Scenario: Refused request
- **WHEN** a sign request is refused because the author does not match
- **THEN** an audit entry `commit.sign_refused` with the reason exists
