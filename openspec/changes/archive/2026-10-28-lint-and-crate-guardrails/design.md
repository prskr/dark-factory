# Design

## Context

See proposal.md, "Why". Current state:

- `.bazelrc` `build:lint` runs `rust_clippy_aspect` with `clippy.toml` and `clippy_flags=-Dwarnings,-Dclippy::too_many_lines`. No Rust target sets `lint_config`, so rustc and clippy under Bazel see only their default lint levels.
- `crate.from_cargo` in `MODULE.bazel` lists 9 of the 17 manifests. crate_universe still resolves every member through the root `members` glob: the lock fix of `split-oversized-test-modules` tracked the hash of `plugins/test-probe/Cargo.toml`, which is not listed.
- The aspect covers 45 Rust targets. Without a target: the `df-harness` unit tests (`src/agent.rs`, `src/mcp.rs`), `df-harness/tests/smoke.rs` and `df-plugins/tests/homelab.rs`.
- `crates/*` inherit `[lints] workspace = true`. `plugins/*` (WASM components) keep their own table with `unsafe_code = "allow"`, because `wit-bindgen` generates `unsafe` code.
- `tools/xtask` is a standalone Cargo workspace (it keeps its HTTP dependencies out of the product's `Cargo.lock`). Its subcommands are dispatched by a `match` on the arguments in `main.rs`.
- CI (`.github/workflows/ci.yaml`) runs only Bazel: `test //...`, `--config=lint` and `--config=fmt`. Cargo is reachable through `bazel run //:cargo`.
- One tracked source file is over 1,500 lines: `crates/df-k8s/src/crd.rs` (4,750 lines, generated by `kopium`).

## Goals / Non-Goals

**Goals:** after this change, adding a lint to the Cargo manifests is the only step needed for both build systems; a crate or test file that escapes the lint run fails a check; the size and naming rules are checks, not guidance.

**Non-Goals:**
- Choosing stricter lints. That is the change `clippy-strictness`.
- Splitting files of 1,000 to 1,500 lines.
- Bazel macros that wrap `rust_library` and friends.

## Decisions

### D1. Bazel reads lints from the Cargo manifests

Every `BUILD.bazel` with Rust targets declares:

```starlark
load("@rules_rust//cargo:defs.bzl", "extract_cargo_lints")

extract_cargo_lints(
    name = "lints",
    manifest = "Cargo.toml",
    workspace = "//:Cargo.toml",
)
```

Every `rust_library`, `rust_binary`, `rust_test` and `rust_shared_library` sets `lint_config = ":lints"`. `.bazelrc` keeps `clippy_flags=-Dwarnings` (rules_rust drops its own `-Dwarnings` once `clippy_flags` is set) and drops `-Dclippy::too_many_lines`.

- **Alternative:** an xtask that generates the `clippy_flags` from `[workspace.lints]`. Rejected: it is a second source plus a generator, and it would not cover rustc lints (`unsafe_code`) or per-crate tables (the plugins).
- **Alternative:** Bazel macros that inject `lint_config`. Rejected for now: they hide 17 one-line attributes behind a new abstraction. D4 checks that the attribute is present.
- **Verification:** rules_rust 0.73 applies `LintsInfo` to rustc. The task verifies that the clippy aspect applies it too, with the negative checks of the spec scenarios. If the aspect ignores the clippy part, the implementer reports it as BLOCKED instead of re-adding flags to `.bazelrc`.
- **Known gap:** `cargo_build_script` (rules_rust 0.73) has no `lint_config` attribute, so the Bazel lint run does not lint the build scripts of `df-proto` and `df-web`. `cargo clippy --all-targets` still lints them. `check-crates` (D4) does not require the attribute on build scripts.

### D2. Missing test targets

- `df-harness`: a `rust_test` with `crate = ":df-harness"` for the unit tests, and a `rust_test` for `tests/smoke.rs`. The smoke tests spawn the built binary. The implementer checks how they locate it and passes it like the `df-plugins` tests do (`data` plus an environment variable). If a test needs a setup Bazel cannot provide, it is tagged `external`. It must not be tagged `manual`, because `//crates/...` skips manual targets and the aspect would not lint them.
- `df-plugins`: `homelab` joins the list of integration tests. Its tests are `#[ignore]`, so the run passes without a Forgejo.

### D3. xtask is linted by the pre-push hook and CI

`tools/xtask/Cargo.toml` gets a `[lints]` table with the same entries as `[workspace.lints]` (it cannot inherit them across workspaces), with a comment pointing to the root table. The pre-push hook runs `cargo clippy --manifest-path tools/xtask/Cargo.toml --all-targets -- -D warnings`, and CI runs the same with the rustup toolchain. `bazel run //:cargo -- clippy` fails with E0463, because the Bazel toolchain has no host std for build scripts. Not yet verified in CI: confirm it on the first PR. xtask stays out of Bazel: a `BUILD.bazel` for it would pull its HTTP dependencies into crate_universe, which the standalone workspace exists to prevent.

### D4. `cargo xtask check-crates`

The check reads files only; it runs neither Bazel nor `cargo metadata`, so it stays fast enough for pre-commit.

For every directory in `crates/*` and `plugins/*` with a `Cargo.toml`:

1. `crates/*` have `[lints] workspace = true`. `plugins/*` have their own `[lints.rust]` and `[lints.clippy]` tables; the check compares both with `[workspace.lints.rust]` and `[workspace.lints.clippy]` and fails on a missing or different entry. `unsafe_code` only has to be present, at any level, so plugins differ only in `unsafe_code`.
2. A `BUILD.bazel` exists, declares `extract_cargo_lints`, and each `rust_library(`, `rust_binary(`, `rust_test(` and `rust_shared_library(` call contains `lint_config`. Calls are split by scanning for these rule names at line start; good enough for buildifier-formatted files.
3. Every `tests/<stem>.rs` is mentioned in `BUILD.bazel` as `tests/<stem>.rs` or as the string `"<stem>"` (the list comprehension of `df-plugins`).
4. `//crates/<name>:Cargo.toml` or `//plugins/<name>:Cargo.toml` is in the `crate.from_cargo` `manifests` list of `MODULE.bazel`.

Errors list every violation at once, each with the file and the fix.

### D5. `cargo xtask check-file-length [<file>…]`

- Without arguments it checks every tracked file (`git ls-files`); with arguments (lefthook's `{staged_files}`) only those files.
- **Source files:** `rs`, `proto`, `wit`, `bzl`, `bazel`, `sh`, `js`, `ts`, `css`, `html`, `toml`, `yaml`/`yml`. Lock files, snapshots, `.sqlx/` and Markdown are not source files.
- **Limit and allowlist,** in the root `Cargo.toml`:

  ```toml
  [workspace.metadata.file-length]
  max-lines = 1500

  [workspace.metadata.file-length.allow]
  "crates/df-k8s/src/crd.rs" = "generated by kopium from the agent-sandbox CRD"
  ```

- **Failures:** a file over the limit without an entry; an entry whose file is missing or within the limit; an entry with an empty reason.
- **Why not `wc -l` in lefthook:** the xtask works on every platform without a POSIX shell, gives readable errors, and keeps the allowlist in a parsed file.

### D6. `cargo xtask check-test-names [<file>…]`

- The check scans `.rs` files for a `#[test]` or `#[tokio::test…]` attribute, then reads the name of the next `fn`.
- A name fails when one of its `_`-separated words matches `finding`, `round\d+`, `r\d+` or `td\d+`, case-insensitive. Bare `review` and `round` are not forbidden: they matched legitimate names (`…_in_review`, `…_round_trips`). `test_review_r12_…` still fails through `r12`.
- There is no allowlist; a false positive is renamed. The current tree passes, since `split-oversized-test-modules` renamed the 34 offenders.
- The rule is a heuristic against the habit seen in the history. It does not judge whether a name describes behavior; the reviewer rule (D8) covers that.

### D7. Hooks and CI

- **lefthook pre-commit:**
  - `check-file-length {staged_files}`
  - `check-test-names {staged_files}` (glob `*.rs`)
  - `check-crates` (glob `Cargo.toml`, `BUILD.bazel`, `MODULE.bazel`, `tests/*.rs`)
- **pre-push:** the xtask clippy run (D3).
- **CI:** a step in `ci.yaml` runs all three checks without arguments (`cargo xtask …`) and the xtask clippy run, both with the rustup toolchain: Bazel's cargo cannot compile xtask (D3).

### D8. Documentation and agent rules

- **`AGENTS.md`, "File structure":**
  - Replace "The thresholds are guidance, not a lint" with the enforced limits, the allowlist location, and the rule that an allowlist entry needs a reason (generated code, or a tracked split).
  - Add a section "Adding a crate": a short checklist covering the directory, `Cargo.toml` with `[lints] workspace = true`, `BUILD.bazel` with `extract_cargo_lints` and `lint_config` on every target, one `rust_test` per `tests/*.rs`, the `MODULE.bazel` manifest entry, and `cargo xtask check-crates`.
- **`.claude/skills/rust/SKILL.md`:** sections "Adding a crate" (Bazel specifics: test targets, `data` for spawned binaries, why `manual` breaks linting, the lock update) and "Lints" (one source; how Bazel picks the lints up; `expect` over `allow`; xtask's mirrored table). Extend the skill description so it triggers on adding a crate or changing lints.
- **`.claude/agents/standards-reviewer.md`:** a check that every new or renamed test is named after the behavior it asserts. A name that is only a topic, or that refers to a review, finding or ticket, is a finding.
- **`.claude/skills/implement-change/SKILL.md`, step 6:** the fix list says that tests are named after behavior, never after finding IDs.

## Risks / Trade-offs

- **The text scan of `BUILD.bazel` (D4) can be fooled by unusual formatting.** → buildifier formats every `BUILD.bazel` (pre-commit hook), so the layout is stable. The check prints the target it could not match, so a false failure is obvious.
- **The word list of D6 can match a legitimate name.** → The match is on a whole word, bare `review` and `round` are not in the list, and a rename is cheap. The current tree has no matches.
- **Enabling `lint_config` under Bazel reveals warnings Bazel did not see before.** → `cargo clippy` already enforces the same lints, so the expected count is zero. Any hit is fixed in this change.
- **The xtask lint table can drift from the workspace table.** → `check-crates` compares the two tables, the same way as for the plugins (D4.1).
