# Proposal

## Why

`docs/tech_debt.md` holds 70 open entries. `implement-change` writes new ones, but no workflow reads them back. Planning does not look at them, the implementer does not, and the review does not. While planning `test-waits-on-conditions` in DF-46, TD-5 and TD-101 described two of the change's fixes and were found only by chance. On top of that, the file is hard to keep in step:
- Each entry exists twice, as a summary row and as a section.
- An "Origin of TD-x" prose list and a "next free ID" line are kept by hand.
- 50 commits touched the file in November 2026, so parallel changes edit the same lines.

## What Changes

- **BREAKING (contributor workflow): one file per entry.**
  - `docs/tech_debt.md` is replaced by `docs/tech-debt/TD-<n>.md`. Each file has TOML front matter (`+++`) for the metadata the tools read: title, severity, area, paths, issue, origin. The prose stays in a Markdown body.
  - The summary table, the origin list and the "next free ID" line go away. The ID counter moves to `docs/tech-debt/NEXT_ID`.
  - `docs/tech-debt/README.md` describes the format and the rules.
  - The "Accepted decisions" section moves to `docs/tech-debt/accepted.md`.
  - The IDs stay the same, so existing references (`TD-27` in `docs/remote-execution.md`, archived review logs) still name the right entry.
- **New `cargo xtask tech-debt` subcommands:**
  - `check`: front matter valid, every path exists, IDs unique, `NEXT_ID` above every ID. It runs in the pre-commit hook and in CI.
  - `list`: prints the summary table that the file keeps by hand today.
  - `for <path>…` / `for --since <rev>`: prints the entries whose paths match the given files, or the files changed since `<rev>`.
  - `for --change <dir>`: takes the repo paths that the artifacts of an OpenSpec change name in backticks. It prints the matching entries whose ID the change's artifacts do not mention, and fails when there are any.
  - `next-id`: prints the next ID and increments `NEXT_ID`.
- **Planning reads the register, however the plan was written.**
  - The `context` of `openspec/config.yaml` gets one sentence: when an artifact names repo paths, run `cargo xtask tech-debt for --change <dir>`. Every reported entry is then named in the proposal, either as fixed (its entry deleted by a task) or under "Out of Scope" with the reason. `context` comes with the instructions of every artifact, so new changes get it, and so do updates that load the instructions.
  - `openspec-update-change` does not load the instructions for every edit. The skill is generated by OpenSpec and overwritten by `openspec update`. The CLI supports `operations` guidance only for `apply` and `archive`. So the guarantee is a gate: `implement-change` preflight runs `for --change`. When an entry is not addressed, it stops and suggests `/openspec-update-change` with the entries. This covers changes written by `openspec-propose`, revised by `openspec-update-change`, or edited by hand.
- **Review reads the register.** `code-review` runs `cargo xtask tech-debt for --since <fixed point>` and passes the result to the standards reviewer. The reviewer reports:
  - a diff that fixes an entry without deleting it (hard);
  - a diff that touches an entry's files without mentioning the entry (judgement);
  - an entry that no longer matches the code (nit).
- **Writing entries.** `implement-change` (step 7.4) writes new P2 entries as files, with the ID from `next-id`.
- **The DF-46 sweep is recorded.** The small cleanup items of task DF-46 (`cleanup-patterns.md`, items 6–10) become entries:
  - cast opt-outs for display values;
  - the wit-bindgen opt-out on the whole crate;
  - the icons follow-up written in a lint reason;
  - the hand-kept `excluded_tests` list;
  - tests that run only in a manual environment.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `build-pipeline`: new requirement "Tech-debt register check".
- `docs-site`: the scenario "No contributor docs" names `docs/tech-debt/` instead of `docs/tech_debt.md`.

## Impact

- `docs/tech_debt.md` removed. New `docs/tech-debt/` (70 entry files, `README.md`, `accepted.md`, `NEXT_ID`).
- `tools/xtask`: new module `src/tech_debt.rs` and dispatch in `src/main.rs`. It uses the existing `toml`, `serde` and `anyhow`, so no new dependency.
- `lefthook.yml` (pre-commit `tech-debt-check`), `.github/workflows/ci.yaml` ("Repository checks").
- Rules for agents: `openspec/config.yaml` (`context`), `.claude/skills/implement-change/SKILL.md` (preflight gate, step 7.4), `.claude/skills/code-review/SKILL.md` (steps 3 and 4), `.claude/agents/standards-reviewer.md` (input and rules).
- Links to the old file: `docs/remote-execution.md` (TD-27), `product/iterations/roadmap.md` (iteration 1.1 row and the "Remaining low-severity tech debt" row), `product/iterations/iteration-3.md` (TD-91, TD-28, TD-31, TD-32). The historical `review_findings.md` and the archived changes stay as they are.
- No production code, no published docs page (the register is contributor documentation and stays unpublished).
- Domain model unchanged: "tech debt entry" is a contributor term, not a product term. No ADR: the format is easy to change again, and `docs/tech-debt/README.md` records it.

## Out of Scope

- A Claude Code hook that shows entries when a file is edited: rejected. It brings debt to the implementer in the middle of a reviewed plan and invites changes outside it. Planning and review are where this is decided.
- Editing the generated OpenSpec skills (`openspec-update-change`, `openspec-propose`): rejected, because `openspec update` overwrites them. If OpenSpec adds `operations` guidance for updates, the rule can move there. Backlog: "Tech-debt rule as OpenSpec update guidance" (row added by this change).
- `TD-n` markers in code comments: rejected. The register stays the only source, and markers go stale.
- Keeping fixed entries with a `resolved` status: rejected. The register's rule stays "delete the entry with the fix", and git history keeps the old text.
- Matching an entry by symbol (function name) as well as by path: rejected for now. Paths are enough to find an entry, and the reviewer reads the symbols in the body.
