## Context

`format_assignment_prompt` (`crates/df-db/src/tasks.rs`) returns one text block: the description followed by `ask_for_title()`. The prompt is stored as JSON in `task_messages.content` (serialized `ContentBlock`s), forwarded in `Assign` / `Prompt`, and the runtime emits it unchanged as `UserMessage.content`. `df-web` renders it with `transcript::blocks_text`, which joins all blocks; the queued stack uses the same function. The assignment prompt is system-authored, so it cannot be edited (`edit_queued_message` only touches human messages). `assign::transcript_summary` reads `userMessage.content[].text.text` from stored events. Instance configuration is `InstanceConfig` (`df-core/src/config.rs`), parsed from the Helm-rendered `config.yaml`.

## Goals / Non-Goals

**Goals:**
- Hide the title instruction from people, keep it for the agent.
- A generic mechanism for later system instructions (webhook notices, monitor wake-ups).
- A way to see hidden blocks when debugging prompts.

**Non-Goals:**
- A configuration page (backlog).
- A runtime-editable setting. The option is static per process like the rest of `InstanceConfig`.
- Per-user visibility or permissions for hidden blocks.
- Hiding agent output or tool calls.

## Decisions

### D1 — A per-block flag on `ContentBlock`
`bool hidden = 10;` next to the oneof (field number outside the existing 1–4, leaves room for more content kinds). Block level, not message level, because the instruction and the description are one message from one author. *Alternative:* a separate `SystemPrincipal` message for the instruction. Rejected: two messages mean two prompt ids and two `UserMessage` events per assignment, and the UI would need the same hiding for a visible author. *Alternative:* ACP `annotations.audience` on blocks. Not used: the flag is Dark Factory's own transcript contract and does not depend on adapter behavior; it can be mapped to an annotation when sending to the harness later.

### D2 — Producers set it, consumers filter it
Only `format_assignment_prompt` sets the flag today. Consumers that show or reuse user text filter: the transcript renderer, the queued stack and `transcript_summary`. The runtime, the harness prompt builder and the audit log (`plain_text`) keep all blocks, so the agent gets the instruction and audit details stay complete.

### D3 — Filtering happens in `blocks_text`
`blocks_text` (both callers: transcript item and queued stack) gets a `show_hidden: bool` parameter. Without the option it skips hidden blocks; with it, hidden blocks stay in the text. The transcript item additionally needs to know which part is hidden to label it, so `ItemKind::User` carries its text as a list of `(text, hidden)` parts instead of a joined string; the component renders hidden parts muted with the label. A message that ends up with no visible part and the option off produces no item.

### D4 — Option `web.showHiddenBlocks`
`InstanceConfig.web: WebConfig { show_hidden_blocks: bool }` (`#[serde(default)]`, `deny_unknown_fields` like `RunsConfig`), Helm `web.showHiddenBlocks: false` rendered in `configmap.yaml`, documented in the control plane configuration reference. `df-web` receives it through its existing state. It is read once at startup; changing it needs a restart (Helm upgrade), which is acceptable for a debugging switch. This is the first option a future configuration view would list, so it lives in the normal config tree instead of a one-off flag.

### D5 — Compatibility
Stored `task_messages.content` and `transcript_events.payload` JSON for old rows have no `hidden` key; deserialization defaults it to `false`. No migration. New rows written before the runtime image is updated: the runtime treats blocks opaquely only if it clones the proto message; a test pins that `UserMessage.content` keeps `hidden`.

### D6 — Notices look like tool rows
`components::transcript::notice` renders a `details` like `tool_row`, with `ml-11`, `data-author="agent"` and a `data-system` marker. The summary is one line: `Icon::BotMessage` (Lucide `bot-message-square`, muted), the code in mono tinted by level (`text-danger`, `text-status-waiting-fg`, `text-muted`), the message truncated, and the turning `ChevronDown`. Opening the row shows the full message, so long notices (an error with a session id) are readable by touch and keyboard, not only through a tooltip. The coloured background boxes are dropped. The stylesheet extends the `[data-tool]` divider rules to `[data-system]` (`[data-tool], [data-system]` and `:is([data-tool], [data-system]) + :is(...)`), so mixed runs of tool and notice rows share one line and live appends regroup without re-rendering. The icon is the same for every level: it marks the source ("the system"), colour carries the severity. The name `BotMessage` leaves `Bot` free for rows generated by the planned minion. *Alternatives:* `info` (generic, no link to a later minion), level-specific icons (more glyphs for what colour already says), a bubble for notices (stays an odd one out), a `title` tooltip for the full message (no touch access).

## Risks / Trade-offs

- [A block with `hidden` could hide user-visible content from reviewers if misused] → only system code sets it; humans cannot (the message form builds visible blocks only). The debug option shows everything.
- [Hidden instructions reduce transparency of what the agent was told] → `web.showHiddenBlocks` and the unchanged audit text cover it; the prompt text lives in code.
- [The summary skips the instruction, so a fallback session after a failed first run asks nothing about the title] → the task keeps its placeholder title and a person can rename it; accepted.
