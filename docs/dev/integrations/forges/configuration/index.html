Plugin configuration

Plugin configuration

Section plugins of the instance configuration (/etc/dark-factory/config.yaml) is a map from plugin name to its settings. The host does not know plugin-specific keys; settings is passed through to the plugin as wasi:config/store. hosts and authScheme are host-side keys: the host enforces them, the plugin never sees them.

plugins:
  forgejo:
    path: /plugins/forgejo/plugin.wasm
    callTimeoutSeconds: 30
    memoryMib: 64
    settings:
      wip-prefixes: "WIP:,[WIP]"
    # no hosts: default plugin
  github:
    path: /plugins/github/plugin.wasm
    authScheme: bearer
    hosts:
      - host: github.com
        apiUrl: https://api.github.com
      - host: ghe.example.org
        apiUrl: https://ghe.example.org/api/v3
KeyRequiredDefaultEffect
plugins.<name>.pathyesnoneComponent file.
plugins.<name>.callTimeoutSecondsno30Upper bound of one plugin call (retries excluded); at least 1 and at most 300, any other value fails startup naming the key. read_pull_request_feedback assumes a call is shorter than its 5-minute next_since overlap, see Review feedback. Guest code is stopped by epoch interruption (50 ms granularity), network waits by a timeout. A timed-out call fails with internal; the instance is discarded.
plugins.<name>.memoryMibno64Linear memory limit per instance. Exceeding it fails the call with internal.
plugins.<name>.hostsno[]Repository hosts this plugin serves. Each entry is a string host[:port] or a map {host, apiUrl}; the map rejects unknown keys. Hosts are DNS names, IPv4 or bracketed IPv6 addresses; they are lowercased, a trailing dot and port 443 are dropped, any other port stays part of the host. A host may be claimed by one entry only. An entry without hosts (or with []) is the default plugin; at most one is allowed.
plugins.<name>.hosts[].apiUrlnohttps://<host>API base URL for this host. Must start with https:// and have no userinfo, query or fragment; host lowercased, port 443 and a trailing / dropped, the path is kept (https://ghe.example.org/api/v3). Becomes the plugin’s base-url and the only authority its requests may reach. Only valid in the {host, apiUrl} form, which rejects unknown keys.
plugins.<name>.authSchemenotokenHow the project’s forge credential is sent: token → Authorization: token <credential>, bearer → Authorization: Bearer <credential>. The host sets the header on every request and replaces one set by the plugin. Applies to all hosts of the entry, the default plugin included.
plugins.<name>.settingsno{}String map handed to the plugin unchanged. The host adds base-url (the route’s apiUrl; for the default plugin scheme and authority of the project’s repo_url) and it wins over a configured one. Keys are documented by the plugin (Forgejo: wip-prefixes, see plugins/forgejo/README.md; GitHub: draft-mode, wip-prefixes, api-version, see plugins/github/README.md).
plugins.<name>.webhookSecretFilenounsetFile with the shared secret the forge signs webhooks with (HMAC-SHA256), read once at startup; trailing line breaks are dropped. Set, it enables POST /webhooks/<name>; unset, that endpoint answers 404. The secret stays in the host: plugins check signatures through webhook-signature.verify. The Helm chart sets it from plugins.<name>.webhookSecret.

Unknown keys fail parsing the configuration. An unknown authScheme value fails startup naming the plugin and the value (see “Startup”).

The Helm chart renders the section from its plugins.* values and mounts each plugin image (//deploy:plugin_forgejo_image, one file /plugin.wasm) as an image volume at /plugins/<name> (deploy/helm/dark-factory/README.md, “Plugins”). All plugins share one Wasmtime engine and epoch clock.

Forge routing

Each forge call is routed by the host of the project’s repo_url, normalized like hosts (lowercase, port 443 dropped). Matching is exact: www.example.org, example.org and example.org:3000 are three hosts. A claimed host goes to the plugin claiming it, any other host to the default plugin. A plugin that did not load keeps its hosts: its projects get a config error naming the plugin and never fall through to the default, because their credential is meant for that forge.

    flowchart TD
    H["host of repo_url (normalized)"] --> C{"listed in hosts?"}
    C -- yes --> CL{"claiming plugin loaded?"}
    CL -- yes --> R1["claiming plugin, base-url = apiUrl"]
    CL -- no --> E1["config error: plugin did not load"]
    C -- no --> D{"default plugin configured?"}
    D -- no --> E2["config error: no forge plugin serves host"]
    D -- yes --> DL{"default plugin loaded?"}
    DL -- yes --> R2["default plugin, base-url = scheme://authority of repo_url"]
    DL -- no --> E1

With more than one plugin, give every entry hosts: a default plugin also receives projects of forges nobody configured (for example gitlab.com sent to Forgejo) and fails with upstream 401/404. Without a default such projects get a clear config error.

Startup

  1. Without a plugins section (or with an empty one) serve uses one entry forgejo with path /plugins/forgejo/plugin.wasm as the default plugin. As soon as plugins has an entry, there is no implicit forgejo.

  2. serve builds the routing table from the configuration alone. A configuration error stops startup before any plugin loads (event “control plane server failed”, field error): invalid `plugins` configuration: <cause> with one of

    • host `<host>` is claimed by plugins `<a>` and `<b>`
    • plugins `<a>`, `<b>` have no `hosts`; at most one default plugin is allowed
    • plugin `<name>`: apiUrl `<url>` must use https://
    • plugin `<name>`: invalid apiUrl (not a URL, or with userinfo, query or fragment; the value is not echoed)
    • plugin `<name>`: invalid host in `hosts[<index>]` (index from 0; the value is not echoed)
    • plugin `<name>`: unknown authScheme `<value>` (use `token` or `bearer`)

    A webhookSecretFile that is missing, unreadable or empty stops startup the same way: cannot read `plugins.<name>.webhookSecretFile` `<path>` or `plugins.<name>.webhookSecretFile` `<path>` is empty.

  3. It loads every entry. An entry that fails (component missing or invalid, memoryMib too large, or no pull-requests export: “is not a forge plugin”) is logged at error (“forge plugin not loaded”, fields plugin, path, error) and stays in the table as unavailable.

  4. If no forge plugin loaded, serve exits with no forge plugin loaded: <every load error>.

  5. Otherwise it logs the table at info: one “forge route” per claimed host (fields host, plugin, available, ordered by host), then “default forge route” (plugin, available) or “no default forge route”.

Each successful load is logged at info (“plugin loaded”) with the fields plugin (name under plugins), path, bytes (component size) and compile_ms (load time: everything after the file read, i.e. import validation, compilation and pre-instantiation; the shared engine is created once before). Use it to see what the plugin costs at startup.

Plugin stderr is logged as event “plugin stderr” with the fields plugin (the name under plugins) and line, at warn for a line that starts with warning: (what the forge plugins write for warnings) and at info otherwise; lines longer than 4 KiB are split.

Per project (database): repo_url (https://<host>/<owner>/<name>[.git], without userinfo, query or fragment) selects the route and gives the repository; base-url comes from the route (see settings). forge_credential_id references the Kubernetes Secret holding the token. Secrets are read per call and not cached.

Add a second forge

  1. Make the component available to the control plane (for the chart: a plugin image mounted at /plugins/<name>).

  2. Add an entry with the hosts it serves, the apiUrl where the API is not at https://<host>, and the authScheme the forge expects. Give the existing entry hosts as well, so neither is a catch-all:

    plugins:
  forgejo:
    path: /plugins/forgejo/plugin.wasm
    hosts: [git.example.org]
  github:
    path: /plugins/github/plugin.wasm
    authScheme: bearer
    hosts:
      - host: github.com
        apiUrl: https://api.github.com

  3. Restart serve and check the “forge route” events: each host with the expected plugin and available=true.

  4. Create projects with a repo_url on the new host and a forge credential for that forge.

Swap a plugin for a host

Projects store no plugin name, so moving a host needs no data change.

  1. Add the new entry (or change path of the existing one to replace only the component).

  2. Move the host from the old entry’s hosts to the new one. Listing it in both fails startup with host `<host>` is claimed by plugins ….

    plugins:
  forgejo:
    path: /plugins/forgejo/plugin.wasm
    hosts: [git.example.org]
  forgejo-next:
    path: /plugins/forgejo-next/plugin.wasm
    hosts: [code.example.org]   # moved from `forgejo`

  3. Check that the projects’ credentials fit the new plugin’s authScheme.

  4. Restart serve; the “forge route” event for the host shows the new plugin. To roll back, move the host back.

Troubleshoot an unroutable project

  1. Read the error of the failed forge call (plugin configuration error: …):

    • no forge plugin serves host `<host>` : no entry claims the host and there is no default plugin, or the host is not valid. Compare the host with the “forge route” events (port and www. count) and add it to the right entry’s hosts.
    • forge plugin `<plugin>` serving host `<host>` did not load: find the startup event “forge plugin not loaded” with that plugin; its path and error name the cause. Fix it and restart.
    • invalid repository URL: repo_url is not https://<host>/<owner>/<name>[.git], or it has userinfo, a query or a fragment. The URL is not echoed: it may carry credentials.
    • repository URL for host `<host>` is not HTTPS: repo_url uses http://; use https://.
    • the project has no forge credential: set the project’s forge credential.

  2. Open the project’s edit form. The hint below the repository URL names the routing result:

    • “Served by the <integration> integration; pull requests and issues use it.”
    • “The <integration> integration claims this host but is not loaded: …”
    • “The default <integration> integration is not loaded: …”
    • “No forge integration applies: …”

    The project list shows the generic Git icon for a project no loaded integration serves (and for a project without a forge credential).

  3. An upstream 401 or 404 instead of a config error usually means the project went to the default plugin. Check the “forge route” and “default forge route” events and add the host to the entry of its forge.

GitHub

The github plugin serves github.com and GitHub Enterprise Server. Its settings, draft modes and error mapping: plugins/github/README.md. The Helm chart’s default values route github.com to it.

Connect a GitHub repository

  1. Check the route: the startup event “forge route” for github.com shows plugin=github and available=true. Without it, add the entry (see “Add a second forge”):

    plugins:
  github:
    path: /plugins/github/plugin.wasm
    authScheme: bearer
    hosts:
      - host: github.com
        apiUrl: https://api.github.com

  2. Create a fine-grained personal access token for an account with write access, restricted to the project’s repositories (“Only select repositories”), with the repository permissions Pull requests read/write, Issues read/write, Contents read/write (Git clone and push) and Metadata read. A classic token needs repo. list-feedback reads each reviewer’s repository permission (GET .../collaborators/{username}/permission), which needs the account’s write access.

  3. Store it in a Secret in the instance namespace (sandbox.instanceNamespace), for example kubectl -n dark-factory create secret generic github-token --from-file=token=<file with the token>.

  4. Settings → Credentials → “New credential reference”: a name, Secret name github-token, key token.

  5. Projects → “New project”: repository URL https://github.com/<owner>/<repo>.git and that credential as forge credential. The hint below the repository URL reads “Served by the GitHub integration; pull requests and issues use it.”

No egress rule for github.com is needed. The sandbox clones and pushes through the gateway’s Git proxy, which sends agent.gitUsername and the token upstream; API calls come from the control plane.

Use title-prefix drafts

The default draft-mode: native creates GitHub’s native draft pull requests, which also exist in private repositories on GitHub Free.

  1. Pick the mode. Use title-prefix when a repository or GitHub Enterprise Server instance rejects native drafts (creating a draft fails with invalid-input naming draft-mode: title-prefix), or for a WIP: marker in the title consistent with Forgejo. auto creates native drafts where possible and falls back to the title prefix elsewhere, at the cost of one failed request per draft and a warning (event “plugin stderr”, plugin=github, level warn).

  2. Set it in the entry’s settings (chart: plugins.github.settings):

    plugins:
  github:
    # path, authScheme, hosts unchanged
    settings:
      draft-mode: title-prefix   # or auto

  3. Restart serve. Open drafts keep working: reading recognizes the title prefix and the native flag.

Add GitHub Enterprise Server

  1. Add the host with its API URL. Settings apply to every host of an entry. A server older than the default API version 2026-03-10 needs api-version: "2022-11-28"; in the github entry that setting would also apply to github.com, so give the server its own entry with the same component:

    plugins:
  github:
    path: /plugins/github/plugin.wasm
    authScheme: bearer
    hosts:
      - host: github.com
        apiUrl: https://api.github.com
  github-enterprise:
    path: /plugins/github/plugin.wasm
    authScheme: bearer
    hosts:
      - host: ghe.example.org
        apiUrl: https://ghe.example.org/api/v3
    settings:
      api-version: "2022-11-28"

    Otherwise add {host: ghe.example.org, apiUrl: https://ghe.example.org/api/v3} to the github entry’s hosts. GraphQL goes to https://ghe.example.org/api/graphql without further configuration.

  2. Restart serve and check the “forge route” event for ghe.example.org.

  3. Connect repositories as above, with a token from the server, repository URLs https://ghe.example.org/<owner>/<repo>.git and an egress rule for ghe.example.org. With a separate entry, the web UI shows these projects with the generic Git icon and the hint names that entry (“Served by the github-enterprise integration; …”).

Bot account access

The forge credential of a project belongs to a bot account. What the factory can do depends on the account’s access to the repository, not only on the token scopes. Three levels matter:

Forgejo

Access of the accountPR create and updateCommentslist-feedbackAuthor rolesWebhook policy members
Readno (unauthorized)no (unauthorized)works; every human is outsideevery human is outsidenever wakes
Writeyesyesworks; every human is outsideevery human is outsidenever wakes
Repository adminyesyesworksmember for write, admin and owner permission, else outsideworks

GitHub

Access of the accountPR create and updateCommentslist-feedbackAuthor rolesWebhook policy members
Readno (unauthorized)no (unauthorized)works; owners, members and collaborators are outsidethose are outsidenever wakes
Write (or admin)yesyesworksmember for write and admin permission, else outsideworks

The role of an author comes from the repository permission lookup (GET .../collaborators/{login}/permission). Forgejo answers it with 403 unless the account is a site or repository admin; GitHub needs push access. When the forge refuses the lookup (403), the plugin does not fail the call. The author is outside, the agent treats the content as untrusted, and a project with the wake policy members does not wake the task for that author. The plugin writes one warning per author and call to stderr, logged at warn as event “plugin stderr” with the field plugin and the text below in line:

ForgeWarning
Forgejowarning: cannot read the repository permission of <login>: the bot account needs repository admin; treating <login> as outside
GitHubwarning: cannot read the repository permission of <login>: treating <login> as outside

So with a Forgejo bot account that has write access only, the review loop works, but every human reviewer is outside. Make the bot account repository admin to get correct roles.

GET .../collaborators/{login} (answers 204 or 404) is not used as a fallback: it needs only read access, but Forgejo answers 404 for the repository owner and for members of the owning organisation, so they would come out outside as well, at the cost of one more request. The backlog has an item for a lookup that works without repository admin.

Forgejo token scopes

The bot account’s token needs write:repository (create and update pull requests, read branches), write:issue (comments on issues and pull requests) and read:user (list-feedback reads the token’s own account to label its comments bot; Forgejo 15 answers 403 without this scope). Read-only use needs read:repository, read:issue and read:user.

Refused requests

A forge answer 401 or 403 becomes the error unauthorized. Only a 403 on the role lookup is turned into outside (see above); a 401 there is an invalid credential and fails the call. Its message starts with the failed request (GET /api/v1/repos/o/r/pulls/7/reviews: token does not have required scope) followed by the forge’s own message. The agent sees it as a tool error (“the forge refused the request (…)”) and is told to ask a human to check the bot account’s access and the project’s forge credential. A missing scope and a missing repository permission look alike; the request and the forge’s message tell which endpoint failed.
